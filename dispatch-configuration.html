1What this screen does

FieldJetX auto-assigns incoming service calls to technicians. Who wins depends on how urgent the job is, and on what that region cares about — arriving fastest, or sending someone who already knows the site.

The screen tunes that per on-call region. Two settings apply to the whole region, and three more are set separately for each tier: Emergency, High and Normal.

SettingScopeWhat it controls
Offer timingRegion Seconds before the next-ranked technician is also offered the job. It paces how fast the cascade widens; it never expires an offer already out.
Search radiusRegion Technicians further away than this are not offered the call.
Scoring strategyTier Rank by speed, by site familiarity, or a weighted blend of the two.
Weight balanceTier For Combined, the split between speed and familiarity. Both halves are stored and always add up to 100.
Wait for acceptTier How long the engine waits before the dispatch escalates to Needs Attention.

Emergency is locked to speed-based ranking, so it has no weight balance on screen and no weight columns on the row.

2The table

One table, dbo.DispatchAutoConfig, one row per on-call region. Loading a region's settings is a single row with no joins: 

SELECT * FROM dbo.DispatchAutoConfig WHERE OnCallRegionId = @region;

19 columns, and no DEFAULT constraints anywhere. Every value is written by the service from the constants in DispatchConfigDefaults.cs; a database default would be a second source of truth to keep in step.

One region's row reads plainly:

OnCallRegionId  F1E98E3D...  (Albuquerque, NM)
Offer timing 30s   Radius 40mi

Emergency  Speed          100 / 0     escalate after 10m
High       Familiarity      0 / 100   escalate after 20m
Normal     Combined        60 / 40    escalate after 30m

No CompanyId. dbo.OnCallRegion has none, and nothing in this database has a foreign key to dbo.Company, so the column could not be validated and could silently disagree with the region. If two tenants ever need the same region configured differently, the fix is a composite unique key, not a loose column.

CHECK constraints are sanity rails only — strategy is one of the three codes, weights 0-100 and summing to 100, escalation 0-1440, offer timing 0-600, radius 1-500. The real limits are enforced in the service layer, so changing a slider range needs no DBA.

3What lives in code instead

Everything static sits in CPCommon/Constants/DispatchConfigDefaults.cs rather than in lookup tables, because none of it varies by customer and none of it is edited by a DBA.

In codeWhy not a table
The three tiers — name, description, card colour, display order, and the rule that Emergency is locked to Speed Fixed definitions, not data. A row per tier bought nothing but a join on every read.
The three strategies — Speed, Familiarity, Combined Same story. A reference table would only earn its place if dispatchers could invent their own ranking methods, and they cannot.
Slider limits and defaults One constant each. If 120s becomes 300s, exactly one line changes — no DDL, no frontend change.

There is no Emergency row in dbo.Priority anyway: it holds 18 rows of per-company free text and every description is NULL, so the tiers could not have come from there.

4API

Two endpoints. Both return BaseInfo, both sit behind the flag ui-enable-auto-dispatch-config.

GET  api/DispatchConfig/GetConfig?onCallRegionId={guid}
PUT  api/DispatchConfig/SaveConfig

GET returns the stored row plus the tier cards and the strategy list assembled from the code constants, so the screen renders generically and keeps no copy of the vocabulary. Tiers and strategies travel as string codes. 

{
  "primaryReturn": {
    "onCallRegionId": "f1e98e3d-...",
    "onCallRegionName": "Albuquerque, NM",
    "offerTimingSeconds": 30,
    "searchRadiusMiles": 40,
    "tiers": [
      { "tierCode": "Emergency", "isRankingLocked": true,
        "strategyCode": "Speed", "speedWeight": 100, "familiarityWeight": 0,
        "escalationMinutes": 10 },
      { "tierCode": "High", "strategyCode": "Familiarity",
        "speedWeight": 0, "familiarityWeight": 100, "escalationMinutes": 20 },
      { "tierCode": "Normal", "strategyCode": "Combined",
        "speedWeight": 60, "familiarityWeight": 40, "escalationMinutes": 30 }
    ],
    "strategies": [ { "strategyCode": "Speed", "strategyName": "Speed-based" } ],
    "meta": { "savedBy": "saravana.rajan", "savedAt": "2026-08-11T10:52:07" }
  },
  "saveError": false,
  "message": ""
}

Save carries only the chosen values. companyId and userId are never accepted from the client — both are resolved server side — and Emergency's strategy and weights are forced regardless of what is sent. 

{
  "onCallRegionId": "f1e98e3d-...",
  "offerTimingSeconds": 30,
  "searchRadiusMiles": 40,
  "tiers": [
    { "tierCode": "High", "strategyCode": "Combined",
      "speedWeight": 60, "familiarityWeight": 40, "escalationMinutes": 20 }
  ]
}

Errors come back as HTTP 200 with saveError set, matching every other endpoint in this API. Nothing throws to the client.

5Why one flat table

An earlier draft split this over four tables — two lookups, a parent and a child. It was reworked flat after the schema review on 10 Aug.

DecisionReasoning
One row per region, no joins Asking the database for a region's configuration returns one plain row. Debugging is reading that row.
Three tiers, three sets of columns The tiers are fixed. A child table meant a parent read plus three child rows plus two reference joins for data that never varies.
Both weights stored The row reads as what the user picked, “60 speed / 40 familiarity”, with no arithmetic, and the sum rule is enforced by a CHECK rather than assumed by every caller.
Strategy as a self-describing string No magic numbers. It also fixed a real bug: when the strategy was inferred from the percentage, choosing Combined and dragging the slider to 0 or 100 reloaded as Familiarity or Speed.
Values per tier, ranges shared Emergency genuinely needs a different escalation wait than Normal. There is no requirement for different limits per tier, so the ranges are one shared constant.
The next setting is a column Adding a column is cheap. A new table means DDL plus backend plus frontend plus another index to maintain.

Also left out on purpose: familiarity lookback (how far back visit history counts is not configurable), ROWVERSION (UpdateDt and UpdateUserId already carry “last edited by”), and a scope discriminator (the unit is settled as the on-call region).

Open questions

  1. Is “the same range for all three tiers” safe? That is the assumption behind sharing one constant.
  2. Who runs the DDL on DEV, and what is the lead time?
  3. Two tenants, same on-call region, different configuration — a real scenario or not?
  4. The tier to dbo.Priority mapping is still open. Nothing above depends on it, but auto-dispatch needs it before it can pick up real jobs.
