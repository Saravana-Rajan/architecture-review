1What this screen does

FieldJetX auto-assigns incoming service calls to technicians. Which technician "wins" depends on two things: how urgent the job is, and what that region cares about — arriving fastest, or sending someone who already knows the site.

This screen lets a dispatcher tune that behaviour per on-call region. For the region as a whole it sets how fast offers fan out and how far the engine will look; for each classification tier (Emergency, High, Normal) it sets how technicians are ranked and how long the engine waits before escalating.

SettingScopeWhat it controls
Time before next offerRegion Seconds before the next-ranked technician is also offered the job. Paces how quickly the cascade widens — it never expires an offer already out.
Search radiusRegion Technicians further away than this are not offered the call.
Ranking methodTier Rank by speed, by site familiarity, or a weighted blend of the two.
Weight balanceTier When the method is Combined, the split between speed and familiarity.
Familiarity lookbackTier How far back visit history counts — 6/12/18/24 months, or All.
Wait for accept before escalatingTier Minutes after everyone eligible has been offered the job before it moves to Needs Attention for a human.

A tier is not a priority. dbo.Priority is per-company free text; a tier is the fixed classification those roll up to. Section 4 explains why they are kept apart, and section 12 records the mapping question still open with the client.

Reading the layout

  • Header row — on-call region select on the left, title and subtitle centred, save-status pill on the right.
  • Two equal columns. Offer timing holds one control (Time before next offer, slider 0–120 in steps of 5, default 30 s). Eligibility & workload holds one control (Search radius, select 10/15/25/40 mi, default 40).
  • Ranking by classification — three equal-height cards, each with a 4 px coloured top bar taken from DispatchTier.ColorHex. Emergency shows a LOCKED badge and a green read-only Speed-based box instead of radios. High and Normal show three radio cards. The weight-balance slider appears only for Combined; the familiarity-lookback select appears for Familiarity-based or Combined. Every card ends with the wait-for-accept slider (0–60 min; defaults 10 / 20 / 30).
  • Future banner — a permanently disabled "Skill / seniority ranking — coming later" row, so the gap is visible rather than silently missing.
  • Sticky footer — scope note plus Reset and Save configuration, both disabled until the form is dirty.

Removed from the earlier design: ETA re-prompts, the workload cap, and the on-site short-circuit. None of them are on the screen and none of them are in the schema.

4What changed, and why

The 5 Aug draft had two tables — DispatchAutoConfig and DispatchAutoConfigPriority — and six columns that are now gone. This section is the important one: the deletions carry more design information than the additions.

Columns that were removed

RemovedWhy it is gone
CompanyId dbo.OnCallRegion has no CompanyId, so a region is not company-owned — OnCallRegionId alone identifies a configuration. And there are zero foreign keys to dbo.Company anywhere in this database, so the column could not be validated: nothing would stop it silently disagreeing with the region it sat next to. A column the database cannot check is a column the database cannot defend.
ScopeTypeId The configuration unit is settled as the on-call region, so the column only ever held 1. A discriminator whose value never varies is noise, and ScopeTypeId = 1 tells a reader nothing. OnCallRegionId is now NOT NULL and UNIQUE, which states exactly the same rule in a form the database enforces.
PriorityId A tier is not a dbo.Priority row. Priority is per-company free text (~8 values such as Overtime Approved and Hot Parts); a tier is the fixed classification those roll up to. That mapping is still open with the client and is deliberately not modelled yet — it belongs in its own table once confirmed, and nothing in these four tables has to change when it arrives.
IsLocked It was always true for Emergency and false otherwise — fully derivable, so storing it per region per tier was storing the same fact three times over. It now lives once, on dbo.DispatchTier as IsRankingLocked (with LockedScoringStrategyId naming what it is locked to) — as data, rather than an if (name == "Emergency") branch in code.
AcceptRejectWindowSeconds The offer model inverted: offers no longer expire. There is no window a technician can miss. Pacing is now StaggerSeconds — how long before the next technician is also offered the job — and escalation is per tier via WaitForAcceptMinutes.
EtaRequestWindowSeconds ETA re-prompts were removed from the screen, so there is nothing to configure.

Open question on CompanyId. Dropping it assumes a given on-call region is configured the same way for every tenant. If two tenants ever need different configurations for the same region, the fix is a composite unique key (CompanyId, OnCallRegionId) with a real constraint behind it — not a loose, unvalidated column reintroduced on its own.

Why reference tables instead of enum columns

The earlier draft stored these as small integers — ScoringStrategyId as a tinyint with 1 = Speed, 2 = Familiarity, 3 = Combined, and the tier implied by a PriorityId. Reading a row then told you "3" and nothing else.

Never map ids manually. Reading a row and seeing "1" tells you nothing — if it's a foreign key, that's a fact. — tech lead, design call, 6 Aug 2026

So DispatchScoringStrategy and DispatchTier are tables, the config rows point at them by foreign key, and one join turns a row into "Combined" instead of "3". The database rejects an unknown strategy because there is no such row, not because a CHECK (… IN (1,2,3)) was remembered.

PK type is uniqueidentifier, matching the house convention: all 8 of the 8 existing small reference tables in this database use one, and there are no integer PKs to be consistent with. TierCode and StrategyCode are the stable programmatic handles — the engine matches on those, never on a generated id and never on the display name, so display text stays safe to reword.

Two tables became four

TableKindCardinality
dbo.DispatchScoringStrategyReference3 seeded rows — Speed, Familiarity, Combined
dbo.DispatchTierReference3 seeded rows — Emergency, High, Normal
dbo.DispatchAutoConfigConfigurationOne row per on-call region
dbo.DispatchAutoConfigTierConfigurationOne row per tier per region — three per config

Both seed scripts are idempotent: re-running inserts nothing and overwrites nothing, so display text edited in place survives a re-run.

6Table — dbo.DispatchAutoConfig

One row per on-call region. Holds the two settings that apply to the whole region.

FieldTypePurpose
DispatchAutoConfigId PKuniqueidentifier Unique id of the row, default NEWID(). The tier table points back at this.
OnCallRegionId FK UQuniqueidentifier The configuration unit, and the only thing that identifies a configuration. NOT NULL and UNIQUE — one configuration per region, enforced by the database. FK to the existing dbo.OnCallRegion; this is what the region select chooses.
StaggerSecondsint "Time before next offer". How long before the next-ranked technician is also offered the job. Paces how fast the cascade widens; it never expires an offer already out. Default 30; screen exposes 0–120 in steps of 5.

InsertDt · InsertUserIddatetime
uniqueidentifier		When the row was created, and by whom.
UpdateDt · UpdateUserIddatetime
uniqueidentifier		 Who last changed it. Rendered on screen as "Last edited by … · …", and what a future optimistic-concurrency check would compare — no separate version column needed. Ranking changes affect who gets work, so the trail matters.

Constraints — UNIQUE (OnCallRegionId), FK → dbo.OnCallRegion, CHECK StaggerSeconds BETWEEN 0 AND 600, CHECK SearchRadiusMiles BETWEEN 1 AND 500. The CHECKs are sanity rails only; the real limits live in the service layer, so changing a slider's range does not need a schema change.

7Table — dbo.DispatchAutoConfigTier

One row per tier within a region — three rows per config, one per card on screen.

FieldTypePurpose
DispatchAutoConfigTierId PKuniqueidentifier Unique id of this child row.
DispatchAutoConfigId FKuniqueidentifier Which region's config this belongs to. What keeps Albuquerque's settings separate from Boston's. ON DELETE CASCADE — delete a config and its three rows clean themselves up.
DispatchTierId FKuniqueidentifier Which classification. FK to dbo.DispatchTier — heading, colour, subtitle, display order and the locked flag all come from there, so nothing is duplicated per region.
DispatchScoringStrategyId FKuniqueidentifier Which radio card is selected. A foreign key, not a number — reading the row and joining once tells you "Combined" rather than "3". Also decides which extra controls render: the weight slider for Combined, the lookback select for Familiarity or Combined.
SpeedWeightPcttinyint The weight-balance slider, 0–100, default 50. 70 means 70% speed / 30% familiarity — familiarity is always 100 − this, so there is no second column to drift out of sync. Kept when the strategy is not Combined, so switching back restores the previous split.
FamiliarityLookbackMonthssmallint NULL The lookback select. How far back visit history counts. NULL means "All" — the screen's last option — rather than a magic 0 or 999.
WaitForAcceptMinutesint "Wait for accept before escalating". Once everyone eligible has been offered the job and this elapses, the dispatch moves to Needs Attention for a human. Defaults 10 / 20 / 30 for Emergency / High / Normal.
IsActive · InsertDt · InsertUserId
UpdateDt · UpdateUserId		bit · datetime
uniqueidentifier		 Same soft-delete and audit set as the parent.

Constraints — UNIQUE (DispatchAutoConfigId, DispatchTierId) (a region cannot have two rows for the same tier), CHECK SpeedWeightPct BETWEEN 0 AND 100, CHECK WaitForAcceptMinutes BETWEEN 1 AND 1440, CHECK FamiliarityLookbackMonths IS NULL OR BETWEEN 1 AND 120. Index — IX_DispatchAutoConfigTier_Config (DispatchAutoConfigId), the read path: the screen loads every tier row for one region.

Emergency gets a row too. Its ranking is locked by DispatchTier.IsRankingLocked, but its WaitForAcceptMinutes is editable — so there is real data to store, and all three tiers are present and symmetric. The old design's "Emergency has no child row" special case is gone.

9API & responses

Two endpoints, both on the FieldJetX BaseInfo envelope and both secured by default via AppControllerBase.

Errors are HTTP 200. The envelope carries the outcome: a failure returns saveError: true with message set — never a 4xx or 5xx. Clients must check saveError, not the status code. This is the existing house contract, not something new here.

All three tiers are required. The server rejects a partial payload rather than guessing what a missing tier meant — a half-sent form cannot silently leave one classification on stale settings.

Success → saveError: false, and primaryReturn is the re-read configuration in exactly the shape GetConfig returns, so the screen reflects what was actually stored.

Two things deliberately absent from every request: companyId and userId. Both are resolved server side from the auth context (_userContext.BuildAppValidationCheck()). Nothing the browser sends can influence whose data is written. CompanyId is no longer a column at all — see section 4.

Emergency is sent, but cannot be changed. Unlike the old design it is in the payload, because its waitForAcceptMinutes is editable. On save the server force-applies the locked tier's LockedScoringStrategyId, overwriting whatever strategy the request carried. A crafted request cannot move Emergency off Speed — and the rule is read from dbo.DispatchTier, not from a name comparison in code.

10Feature flag

The whole feature is gated by one LaunchDarkly key.

ui-enable-auto-dispatch-config

  • Angular — the /systemConfig/dispatch-configuration route and the Dispatch Config nav item are both behind it. Flag off: no menu entry, and the route does not resolve.
  • API — both GetConfig and SaveConfig check it too. Gating only the UI would leave the endpoints reachable by anyone who knows the URL, so the check is enforced on the server as well as hidden on the client.
  • Fails closed. If the flag cannot be resolved — LaunchDarkly unreachable, SDK not initialised, key missing — it defaults to off. An outage can hide a finished feature, which is recoverable; it can never expose an unfinished one, which is not.

11Design decisions

Four tables, not two

Two different "per" — settings per region (stagger, radius) and settings per tier (method, weight, lookback, wait) — plus two reference tables that are seeded, not configured. Splitting reference from configuration is what removes the magic numbers.

Foreign keys over enum columns

"If it's a foreign key, that's a fact." An unknown strategy is impossible because the row does not exist — no CHECK (… IN (1,2,3)) to remember to update, and a SELECT is self-describing.

Codes, not names, not ids

The engine matches TierCode / StrategyCode. Ids are generated per environment, and display names get reworded by whoever owns the copy. Codes are the only thing safe to branch on.

One weight column, not two

Familiarity is always 100 − SpeedWeightPct. Two columns would mean an invariant to validate and a way for the pair to drift apart. The UI already works in whole percentages.

NULL means "All"

FamiliarityLookbackMonths is nullable rather than using 0 or 999 as a sentinel. "No limit" is genuinely the absence of a value, and a sentinel would eventually be summed or compared by accident.

The lock lives on the tier

Stored once on dbo.DispatchTier instead of on every config row, so it cannot be inconsistent between regions — and enforced on save, not just disabled in the UI.

EF, not stored procedures

CPData.Repository already calls SaveChangesAsync 329 times, so this matches existing practice. It also keeps the DBA dependency down to running two DDL scripts.

Bounds in the service, rails in the schema

CHECK constraints are wide sanity rails (0–600 s, 1–500 mi, 1–1440 min). The real limits are the service's, so changing a slider from 120 s to 180 s does not need a DBA ticket.

Deliberately left out

ROWVERSION concurrency (UpdateDt would serve), a Priority→Tier mapping table (still open with the client), and the skill / seniority ranking on the disabled banner. All cheap to add; none cheap to remove once depended on.

12Open questions

Things that need a decision before or shortly after this ships.

1 · Priority → Tier mapping is unresolved. dbo.Priority is per-company free text (~8 values such as Overtime Approved, Hot Parts) and none of them is a clean "Emergency". A tier is the fixed classification those roll up to, and the mapping is deliberately not modelled yet — it belongs in its own table once the client confirms it. Until then the engine needs an agreed interim rule for turning an order's priority into a tier. Nothing in these four tables has to change when the mapping table arrives.

2 · Is one configuration per region right for every tenant? CompanyId is gone because dbo.OnCallRegion has none and nothing in the database could have validated it. If two tenants must configure the same region differently, we add a composite unique key (CompanyId, OnCallRegionId) — a schema change with a real constraint, not a loose column. Cheap now, expensive after there is data.

3 · Who owns the tier display text and colours? TierName, TierDesc and ColorHex are seeded and editable in place, and the seed script never overwrites them. If the client wants different wording or accents, that is a one-row UPDATE per environment — but someone needs to own it.

Also open: when the feature flag is turned on per environment, and who runs the DDL for DEV / QA / STG.

13Migration & status

FieldJetX has no migration framework. Verified in the codebase: 0 EF migration folders, 0 .sqlproj, 0 .dacpac, 0 CREATE PROCEDURE scripts.

The database is the source of truth — fieldgeticsContext was reverse-engineered from it. So "migration" here means handing the DBA a SQL script, not running a tool.

ScriptOrderContents
01_dispatch_lookups.sqlFirst DispatchScoringStrategy + DispatchTier, with idempotent seed data (3 rows each).
02_dispatch_auto_config_tables.sqlSecond DispatchAutoConfig + DispatchAutoConfigTier and the read-path index. Its foreign keys reference script 01, so the order matters.

Both scripts are guarded (IF NOT EXISTS) and safe to re-run: existing tables are skipped, seed rows are inserted only when missing, and display text edited in place is never overwritten. Neither carries a USE statement — run them in the target database's context, matching the other DDL scripts in the repo.
